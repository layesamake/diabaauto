# Journal des décisions et des écarts — Diaba Auto

> Créé conformément à `CLAUDE.md` §2 : « Consigner le conflit avec ses conséquences dans `docs/decisions.md` ».
> Le schéma `prisma/schema.prisma` est une **proposition de référence non validée** (`CLAUDE.md` §2).
> Les écarts documentaires exhaustifs (E01–E31) et les règles de migration/seeds exigées par les documents sont conservés en annexe à la fin de ce fichier.
>
> **2026-09-28 — changement de corpus de référence.** `docs/` contenait un sous-ensemble renommé de
> 16 documents ; il a été remplacé par le jeu canonique de 21 documents (`01_PRD` → `21_Prompt_maitre`).
> Les deux jeux sont **deux générations différentes** : le schéma de référence compte 37 modèles et
> 17 enums (doc 12) contre 18 modèles et 10 enums pour celui employé au lot 2, et il impose le
> snake_case sur toutes les colonnes. Les décisions et écarts ci-dessous qui portent sur les noms de
> documents ont été remappés vers la numérotation canonique ; ceux qui portent sur le **modèle de
> données** sont réexaminés dans `docs/audit-alignement-corpus-schema.md`. Le constat « aucun écart de
> structure » de l'annexe (E01) est **caduc contre le corpus canonique** et n'a pas été réécrit : il
> reste la preuve de l'analyse menée contre le jeu précédent.

## Partie A — Décisions techniques prises (réversibles, aucun arbitrage produit requis)

| # | Sujet | Décision | Justification |

| T01 | Outil de migration unique | **Prisma Migrate** est la source de vérité du schéma ; les objets que Prisma n'exprime pas (contraintes `CHECK`, index partiels, trigger `auth.users`, RLS, policies, buckets Storage) sont ajoutés dans des **migrations SQL versionnées du même dossier** `prisma/migrations/`, appliquées par le même outil. Le SQL de structure est produit par `prisma migrate diff --from-empty --to-schema-datamodel`, jamais écrit à la main, pour éviter toute dérive schéma/SQL. | `CLAUDE.md` §10 impose une seule procédure de migration ; RLS et contraintes sont exigées par les docs 11 / 12 / 17 et ne sont pas exprimables en Prisma. |
| T02 | Ordre et découpage des migrations | L'ordre documenté `M01 → M05` (doc 13) est conservé : `M01` extensions/enums/profils/rôles/permissions, `M02` référentiels/véhicules/images/documents, `M03` favoris/recherches/prospects/demandes/commandes/événements, `M04` journaux d'état + audit + contraintes SQL + index et unicités, `M05` RLS + fonctions + buckets Storage. | Les dépendances de clés étrangères respectent déjà cet ordre ; aucune raison de dévier. |
| T03 | Liaison `auth.users` ↔ `profiles` | Trigger SQL `AFTER INSERT ON auth.users` **idempotent** (`ON CONFLICT (auth_user_id) DO NOTHING`) créant `profiles` (`CUSTOMER`, `ACTIVE`) puis `customer_profiles`, plus une fonction de réparation des comptes orphelins. `user_type` et `status` ne sont **jamais** lus depuis `raw_user_meta_data` ni depuis un champ éditable par l'utilisateur. | Doc 11 : création de profil « idempotente via mécanisme serveur ou trigger maîtrisé », « contrôler les comptes orphelins » ; doc 11 et `CLAUDE.md` §6 : aucune attribution STAFF/ADMIN depuis des métadonnées éditables. |
| T04 | Vérification des montants | Contraintes `CHECK` : `vehicles.public_price >= 0`, `vehicles.reseller_price >= 0`, `orders.agreed_price >= 0`, `custom_requests.budget_min >= 0`, `budget_max >= 0`, et cohérence `budget_min <= budget_max` lorsque les deux sont renseignés. | Doc 12 : « contraintes CHECK SQL pour montants non négatifs, dates cohérentes et statut ». |
| T05 | Audit append-only | `audit_logs` : `REVOKE UPDATE, DELETE` + trigger `BEFORE UPDATE OR DELETE` levant une exception, en plus de l'absence de toute méthode de modification dans le service. | Doc 12 (« append only »), doc 17 (« audit append-only »). |
| T06 | Index manquants | Ajout des index sur clés étrangères non couvertes (`staff_roles.role_id`, `leads.customer_id`, `leads.vehicle_id`, `orders.vehicle_id`, `audit_logs.actor_profile_id`, `custom_requests.customer_id`) et d'un index partiel catalogue `vehicles (published_at DESC) WHERE is_published = true`. | Doc 12 : « index sur clés étrangères, statut, publication, localisation, marque, prix et date de création » ; `CLAUDE.md` §9. Mise à jour lors de l'alignement canonique : les rôles du personnel étant N:N, l'index porte sur `staff_roles`, et la publication n'étant plus un statut mais `is_published`, l'index partiel filtre sur ce booléen. |
| T07 | Format des migrations | Dossiers horodatés Prisma (`AAAAMMJJHHMMSS_nom`) avec le libellé documentaire en clair (`m01_identite`, `m02_referentiels`, …). | Doc 13 ne fixe aucune convention (E20) ; format imposé par l'outil retenu en T01. |
| T08 | Limitation de fréquence | Limiteur à fenêtre fixe, en mémoire, seuils paramétrés par variables d'environnement (`RATE_LIMIT_*`), désactivé hors production sauf activation explicite. | Doc 17 impose la mesure mais ne chiffre aucun seuil ; valeurs **à valider** (D07). |
| T09 | Durée des URL signées | Paramétrée (`STORAGE_SIGNED_URL_TTL_SECONDS`, 300 s par défaut). | Doc 11 : « URL signée courte durée » sans valeur (D08). |
| T10 | Tests nécessitant une base | Les règles métier sont testées unitairement via des ports (interfaces), sans base. Les tests d'intégration Prisma/RLS/Storage sont écrits mais **non exécutés** faute de base non productive accessible ; ils sont marqués comme tels dans le rapport de lot. | `CLAUDE.md` §12 : ne pas annoncer une vérification non exécutée ; `CLAUDE.md` §10 : ne pas développer contre la production. |
| T11 | Erreurs fonctionnelles | Codes d'erreur imposés par le doc 10 centralisés dans `lib/errors.ts` (`UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION`, `CONFLICT`, `RATE_LIMITED`) ; enveloppe de réponse normalisée `data` / `error { code, message, correlationId }` au niveau route/Server Action, jamais au niveau service. Aucun détail SQL ni trace interne renvoyé au client. Un code technique supplémentaire `INTERNAL` (non fonctionnel, non documenté) sert uniquement aux défaillances inattendues : le message reste générique et la cause est conservée côté serveur. | Doc 10 (contrat transversal), doc 07 (« la réponse d'un accès interdit ne doit exposer ni l'existence d'une ressource privée ni aucun détail interne »). |
| T12 | Ordre de contrôle serveur | Toute opération privée suit l'ordre imposé : session → statut du compte → permission → portée/propriété → validation → exécution + audit dans une transaction. Implémenté dans un unique garde `requireStaff` / `requireCustomer` pour empêcher toute divergence entre Server Actions et Route Handlers. | `CLAUDE.md` §6 ; doc 10. |
| T13 | Enveloppe unique pour toutes les Server Actions | Les actions d'authentification et celles de My Diaba Auto renvoient la même enveloppe `data { message, … }` / `error { code, message, correlationId, fields? }`. Les anciennes formes ad hoc (`{ status, message, fields }`) sont supprimées. | T11 (doc 10) : une seule forme de réponse, un seul endroit où les erreurs sont normalisées ; évite qu'un formulaire affiche un échec comme un succès. |
| T14 | Permission d'entrée du back-office | `/admin` exige `requireStaff(actor, "vehicle.view")` : la plus faible permission opérationnelle, présente chez ADMIN et chez le COMMERCIAL provisoire (D01). Le portail n'affiche que l'état d'attente du lot ; aucun écran d'administration n'est ouvert aux commerciaux. | Doc 07 §Acteurs : « Commercial — back-office opérationnel selon habilitation » ; une porte sur `analytics.view` ou `audit.view` exclurait tout commercial du back-office, ce que les documents n'énoncent pas. |
| T15 | Contrôle anti-dérive de la matrice de droits | `tests/unit/seed-data.test.ts` échoue si un droit du rôle ADMIN ou COMMERCIAL, la liste des 26 permissions ou la correspondance avec `services/permissions.service.ts` changent sans décision mise à jour. Étendu lors de l'alignement canonique : le module de chaque permission et la description de chaque rôle sont également contrôlés. | E15/E16 : la matrice provisoire D01 doit rester explicite et vérifiée, jamais modifiée silencieusement. |
| T16 | Tarif Revendeur et privilèges de colonnes | `vehicles` n'est **jamais** exposé au client par un `GRANT SELECT` global : le privilège est accordé colonne par colonne et `reseller_price` en est **exclu**. Le tarif Revendeur n'est servi que par le serveur (`service_role`) via `services/pricing.service.ts`. | Doc 07 §3 (« voir prix Revendeur : Non » pour visiteur et Standard) et doc 17 §1 (menace « accès tarif Revendeur »). RLS filtre des **lignes**, pas des colonnes : sans ce privilège ciblé, une requête PostgREST directe lirait `reseller_price` malgré la policy. Contrôlé par `scripts/verify-migrations.mjs`. |
| T17 | Alignement du schéma sur le corpus canonique | Convention unique : **snake_case en base via `@map` sur chaque champ** ; enums du corpus (`ProfileStatus`, `PricingProfile`, `CustomerSegment`, `ResellerStatus.NOT_APPLICABLE`, `VehicleCommercialStatus`, `LogisticsLocation` avec `IN_TRANSIT`, `DocumentVisibility`, `LeadStatus`, `OrderStatus`) ; tables canoniques (`staff_roles`, `favorite_vehicles`, `vehicle_media`) ; `vehicles.is_published` distinct du statut commercial. | D20 : le corpus canonique (doc 12, déclaré « faisant foi » par le doc 03) remplace la génération précédente employée au lot 2. Aucune migration n'ayant jamais été appliquée, l'alignement est sans reprise de données. Détail : `docs/audit-alignement-corpus-schema.md`. |
| T18 | Modèle d'autorisation du personnel | L'activité d'un membre du personnel est portée par `profiles.status` (`ACTIVE` = authentifié) ; les rôles sont N:N via `staff_roles` ; les permissions effectives sont l'**union dédupliquée** des permissions de tous ses rôles, et un membre sans rôle n'a **aucun** droit (refus par défaut). `staff:grant` ajoute un rôle par upsert sur `(staff_id, role_id)` sans jamais retirer les autres ni réécrire l'identité du membre. | Doc 12 (`StaffRole` N:N, aucun champ `active` sur `staff_profiles`) et doc 07 §1 (« least privilege : permissions explicites »). Le retrait de rôle reste à outiller (D03). |
| T19 | Tables de prix livrées avec L2, logique au L3 | `vehicle_prices`, `exchange_rates` et `price_history` sont créées avec le lot L2 (doc 12, doc 03 §9) et `vehicles` **perd** `public_price`/`reseller_price`/`currency` : exécution de D10. `services/pricing.service.ts` lit désormais des lignes de prix (règle inchangée : tarif Revendeur réservé à `resellerStatus = APPROVED`, repli Standard avec anomalie `MISSING_RESELLER_PRICE`). L'upload de fichier (API Storage, URL signée) est isolé et **non exercé**. | D15 (aucun projet Supabase) et doc 03 §7 (média image/vidéo, une seule image principale) ; `CLAUDE.md` §12 interdit d'annoncer une vérification non exécutée. |
| T22 | Invariant de publication d'un véhicule | Un véhicule ne peut être publié (`is_published = true`) que s'il porte marque, modèle, année, état, localisation, **au moins un média image principal public** et **au moins un prix actif Standard**, sinon refus `VALIDATION`. Pagination serveur bornée (12 par défaut, 24 maximum) et tri **toujours** départagé par `id` pour rester déterministe. | Doc 03 §1 et §6 (données d'approvisionnement non publiques), doc 17 §1, doc 18 §6 (« pagination serveur, index DB, payloads courts »). ## Procédure de migration exigée par les documents

**Ordre unique et identique sur tous les environnements** (doc 13) :

1. **M01** — extensions nécessaires, enums techniques, `profiles`, rôles et permissions.
2. **M02** — référentiels marques, modèles et caractéristiques ; véhicules, images, documents et prix.
3. **M03** — favoris, recherches enregistrées, prospects (`Lead`), demandes personnalisées (`CustomRequest`) et commandes.
4. **M04** — journaux d'état (`OrderEvent`), audit, contraintes SQL, index et unicités.
5. **M05** — RLS, policies, fonctions et buckets Storage ; vérifier les privilèges par rôle.

**Procédure de livraison** (doc 13) : créer la migration en développement → relire le SQL et le plan de retour → appliquer sur base de test → exécuter les tests de données et de politiques → préproduction → production avec sauvegarde vérifiée et fenêtre de changement.

**Migrations destructives** : deux temps — ajout compatible → bascule applicative → retrait ultérieur.

**Retour arrière** : rollback applicatif indépendant de la base ; une migration appliquée reste compatible avec la version précédente pendant la bascule ; restauration de sauvegarde uniquement sur décision d'incident ; après chaque migration, comparer version attendue, cardinalités, contraintes, politiques et parcours critiques.

**Environnements** : développement, préproduction et production séparés, dans le même ordre ; les previews ne doivent pas accéder à la base de production ; aucune migration de production sans autorisation explicite (`CLAUDE.md` §10).
